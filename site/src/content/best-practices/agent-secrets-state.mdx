An agent prompt is code. It gets stored in files, pasted into wikis, shared with teammates, and occasionally committed to Git. A raw API key in that prompt is a leak waiting to happen — and unlike a `.env` slip, it's harder to spot because the prompt looks like documentation. [Practice 07](/best-practices/secrets) keeps secrets out of the repo. This practice keeps them out of the prompt.

The second failure mode is state ambiguity. An agent that doesn't know whether it's running in dev or prod will eventually do something expensive in the wrong place. "I assumed dev" is not a post-mortem anyone wants to write.

### The two rules

1. Secrets enter via environment variables. The prompt holds the variable name, never the value.
2. The agent reads `$ENVIRONMENT` explicitly and confirms it before any write action (insert, update, delete, deploy).

If a required secret is missing, the agent halts and surfaces a clear error. It does not substitute a default, guess, or continue silently.

### How to do it

<Step n={1}>
Write every agent prompt with env-var references, not values. Use `$DATABASE_URL`, not `postgres://user:pass@host/db`. The prompt template ships in the repo; the values stay in `.env`.
</Step>

<Step n={2}>
Add an environment confirmation block at the top of every agent prompt. The agent's first output in any session must list: the active environment name and which secrets it can access.
</Step>

<Step n={3}>
Copy the prompt template below into your agent file. Fill in `[PROJECT NAME]` and `[TASK DESCRIPTION GOES HERE]`. Add or remove secret references to match your actual stack.
</Step>

<Step n={4}>
Add the matching `.env` shape to your repo's `.env.example`. Keep test values obviously fake (`test-key-do-not-use`). The `.env` with real values stays gitignored.
</Step>

### Agent prompt template

```
You are a coding agent working on [PROJECT NAME].

## Environment
Active environment: ${ENVIRONMENT}
You have access to the following secrets via environment variables:
- $DATABASE_URL
- $API_KEY
- $WEBHOOK_SECRET

Before taking any write action (insert, update, delete, deploy),
confirm the active environment and list the secrets you can access.
If any required secret is missing, halt and output:
"MISSING SECRET: [variable name]. Cannot proceed."

Never hardcode credentials. Never substitute default values for missing secrets.
Never infer the environment — always read from $ENVIRONMENT explicitly.

## Task
[TASK DESCRIPTION GOES HERE]
```

### Matching `.env` shape

```
ENVIRONMENT=dev
API_KEY=test-key-do-not-use
```

The `ENVIRONMENT` variable is not optional. Every environment — dev, staging, prod — sets it explicitly.

### Acceptance criteria

- Run the agent in dev without it touching prod data.
- A teammate clones the repo and runs it without receiving credentials out-of-band.
- The agent's first output in any session confirms: environment name and which secrets it has access to.

<Callout tone="warning">
If a secret is missing and the agent substitutes a default or continues without it, that's a bug in the prompt, not a graceful fallback. The agent must halt. Silent failures in prod are worse than loud failures in dev.
</Callout>

<AntiPatterns>
- Putting a real token in the prompt "just for testing." It's now in your session history and any transcript tool that reads it.
- Letting the agent infer `dev` because there's no `$ENVIRONMENT` set. Set it explicitly in every environment.
- Using a default value when a secret is missing (`API_KEY=${API_KEY:-fallback}`). This masks the missing config.
- Sharing agent prompts over Slack without checking for hardcoded values first.
</AntiPatterns>
